# Vice and Virtue — project context

A hybrid PWA party game — a Werewolves spinoff. 6–20 in-person players, each holding their secret role on their own phone. Built solo by Matthijs (idea owner, first-time coder) with AI assistance. Live and playtested.

If you are a fresh chat session: read this file first, then `AGENTS.md` for the Next.js version warning. Together they're enough to be productive.

---

## Stack

- **Next.js 16.2.6** — App Router, React 19, TypeScript, Tailwind v4, Turbopack
- **Supabase** — Postgres + Realtime + Auth + Storage. Game tables use open RLS for MVP (must tighten before launch); account tables (`profiles`, `friendships`, `user_achievements`) use real per-user RLS.
- **Vercel** — hosting, auto-deploys from `main`
- **`@tabler/icons-react`** (^3.44.0) — icon set used across the start-screen hub (sidebar, bottom-nav, HUD)
- **`framer-motion`** — hub entrance/stagger animations (installed when the hub restyle started importing it)

**This Next.js version differs from older training data — always read `node_modules/next/dist/docs/` for the relevant API before writing Next.js code.** (`AGENTS.md` says the same.)

## Game design (current)

- **Players:** 6 min, 16 optimal, 20 max. Target session ~30–45 min.
- **Camps:** Vice vs Virtue. **12 default roles** (see "Roles" below) + **8 unlockable roles** (migrations 062+065; LP price by tier — **S 2500 / A 1500 / B 1000 / C 600**, migration 079; once unlocked they're **pickable in role select**, and all 8 have their abilities fully implemented — migrations 066–068). Balanced assignment by tier S→A→B→C→D, equal camp counts (virtues get the extra on odd N). **Exactly one C-tier role per camp per game** (migration 057): each camp has two C roles (Vice: Torment/Vengeance, Virtue: Truthfulness/Sacrifice) and one is chosen at random per game, so a full camp is S,A,B,C,D then D-tier filler. (Was two C roles → S,A,B,C,C,D.)
- **Day cycle — three named phases (Reflection / Action / Consultation), each spanning sub-phases:**
  - **Reflection** — role-action (30s) → event_summary (host-advance) → minigame (95s) → result (host-advance)
  - **Action** — outreach (120s one-on-one chats; **mandatory**, imprisoned players ARE eligible, DM history resets each day) → store (60s individual potion shopping + Fanaticism check/detonate + Sacrifice, `store` phase, migration 058 — see "Store & potions") → **store_summary** (anonymous recap of the shop's deaths — combat potions, bomb detonations, sacrifices, migration 072). The **camp abilities (Revealing Eye, freeing a prisoner) now live IN the store** (migration 092) and the separate `group_action` phase was **removed**. The **whole Action phase shares the outreach background**.
  - **Consultation** — the imprisonment vote (95s + 1 re-vote on tie) → new_day (4s splash). The `group_action` camp-ability phase was **removed entirely** (migration 092 — its powers are store potions/funding now), so Consultation = the imprisonment vote only.
- **Pre-game flow (once at start):** depends on `rooms.role_assign_mode` (migrations 063+064; the host flips it in the lobby, **new lobbies default to 'choose'**; ranked is always 'choose'):
  - **'choose':** start/match → **role_select** (30s: each player is dealt a camp + a tier and picks their role within it; a click is a tentative pick camp-mates see **anonymously by tier** in a team panel — desktop left, mobile bottom — then "Lock in"; on expiry the host resolves, stragglers get their tentative pick else a random role of their tier) → **role_overview** (this game's full cast, Vice | Virtue, majority-continue) → lore_intro → **straight into the first role_action** (no role_reveal — you picked your own card).
  - **'random' (the classic deal):** start → secret deal (per-tier roles from the host's **role_config**, validated by `vv_config_slot`; unset slots fall back to defaults, C random of its two) → **role_overview** → lore_intro (3.5s zoom + 0.5s fade-to-black) → role_reveal → first role_action.
  - The old **game_overview** tutorial screen is retired from the flow (unreachable; the Walkthrough lives on in "How to play").
- **Player states:** active / in_prison / in_hospital (1 day) / dead. Imprisoned and hospitalized players can still be vote targets; dead players cannot.
- **Spectator modes (migration 093):** non-active players stay in the game as spectators instead of a passive "you can't act" screen.
  - **Dead = omniscient spectator** — routed (in `app/room/[code]/page.tsx`) to **`DeadSpectator.tsx`** for the secret phases (role_action / minigame / outreach / store / consultation). It polls the **dead-gated** `spectator_secrets(player)` RPC every ~2.5s (returns every player's role, Soul Energy, queued role action, vote, Quiz guesses, and Market purchases — **only when the caller is dead**, else `{ok:false}`) and shows the relevant secret per phase: roles+SE+actions; each player's V/V/? tags; **all** private DM threads (open-RLS `dm_messages`); who bought what; who voted for whom. Plus `DeadChat`. Summary/splash phases (event_summary/result/store_summary/new_day) the dead still see via the normal components.
  - **Hospital + Imprisoned = read-only** — `Minigame`/`Store`/`Consultation`/`RoleAction` dropped their passive early-returns: they now render the **normal screen with the action region wrapped in `pointer-events-none opacity-60`** (when `!canAct`) + a "you can watch but can't act" banner, and the Done/submit button hidden. **Exception:** imprisoned **Vengeance** keeps her revenge ability, and in **Outreach** both hospital + prison **can chat** (`eligible = !dead`; was `!dead && !in_hospital`). (Consultation group-chat sending is still allowed to them, as before — only the *vote* is disabled.)
- **The Wandering Soul (migration 094) — a neutral "anomaly" role for ODD player counts.** `assign_roles_and_start` carves out exactly **one** `wandering_soul` (camp **`neutral`**) whenever the count is odd, so the remaining even number splits equal Vice/Virtue (even counts are unchanged). It's kept out of the camp/unlock matrices, role-config + badge matrix (via the `RoleDef.anomaly` flag + `isAnomalyRole`), but shown in its own **Anomaly** row beneath the Vices/Virtues in the hub Roles tab (page.tsx) and How-to-play's Anomaly section. `Camp` is now `vice | virtue | neutral`; `vv_role_camp('wandering_soul') = 'neutral'`, so it counts for **neither** camp (never blocks a camp win) and any **Quiz** V/V guess about it is **always wrong** (zeroes the guesser — tag it "unknown"). **Wins by escaping:** in Role-action he guesses every active player's camp (`WanderingSoulAction` → `submit_soul_escape`, held in `player_secrets.soul_escape_guess`); the host runs `resolve_soul_escape` right after `resolve_role_action` — all correct ⇒ `rooms.winner='neutral'`, phase `soul_victory_intro` → game_over (he alone wins; `recordGameResults(room,'neutral')`). **Ward (his role ability, in the Role-action phase — NOT a market potion):** `buy_soul_ward` (100 SE, soul-only, phase `role_action`) sets `potion_protect` (kill/hosp — honoured by that same reflection's `resolve_role_action`) + `potion_soul_protect` (blocks that day's consultation imprisonment in `resolve_consultation`) for one cycle. Both the ward + the escape guess live in `WanderingSoulAction` (rendered in `RoleAction`). When present, the Soul shows in the in-game **cast** (`RoleOverview`, a neutral "Anomaly" card). (The old one-time **`wandering_soul_intro`** notification after `lore_intro` was removed as redundant with the cast — `endLoreIntro` now goes straight to the role reveal / first action; the phase + `WanderingSoulIntro.tsx` remain in the tree but are no longer entered.) Art: `public/cards/wandering_soul.png` + `public/role-icons/wandering_soul.png`.
- **Win conditions:**
  - All Virtues imprisoned/dead → Vices win
  - All Vices imprisoned/dead → Virtues win
  - **Wandering Soul escapes** (guesses every active camp) → **Soul wins**, `soul_victory_intro` → game_over (neutral; camps both lose)
  - (The old **Murder + 1 instant Vice win** endgame was **removed** — migration 090 — since a lone Virtue can still win with the store potions; the game now plays on until a whole camp is imprisoned/dead.)
  - Vice win → `vice_victory_intro` screen → game_over scoreboard
  - Virtue win → `virtue_victory_intro` screen → game_over scoreboard
- **Soul Energy:** `round(100 × 0.93^(rank−1))` for rank x (capped at rank 20). **Starting SE = 100.** **Speed is not a factor** — ties on raw Quiz score **share a rank** (standard competition ranking, e.g. 5,5,3 → ranks 1,1,3) and so earn the **same** SE (`rankPlayers` in `scoring.ts`; `minigame_submitted_at` is no longer used for tie-breaking). **Any wrong V/V tag in the Quiz zeroes both the raw score AND the SE awarded for that round** (Unknown / "?" still counts +0.4 raw, no penalty).
- **Minigame = points vs information (intentional, do not "fix"):** the scoring is a deliberate tradeoff, not a degenerate one. Tagging everyone "?" banks safe SE — the **points** path. Committing 1–2 V/V reads is the **information** path: you form a concrete read to argue in discussion, and it feeds the shared post-minigame clue (`rooms.minigame_clue`, shown on Result + the consultation vote), at the risk of the wrong-guess zero. Designed asymmetry: **Vices tend to bank points** (fuel their aggressive kit), **Virtues tend to invest in reads** (they must find the Vices). All-"?" is a valid strategic choice. (Confirmed by Matthijs 2026-06; an earlier review wrongly flagged this as broken.)
- **Player names:** duplicates auto-prefixed "1. Alex" / "2. Alex" by join order.

### Camp abilities — folded into the store (migration 092)

The separate `group_action` phase is **removed**. Its two camp powers became market-phase mechanics, available to anyone (no more camp-restricted votes):

- **Revealing Eye** — a **150 SE store potion** (instant, **private to the buyer**): returns the count of still-active Vices and Virtues (`buy_potion` `'eye'` branch — no target, no armed flag, repeatable). *(Was a Vices-only Yes/No vote broadcast to everyone.)*
- **Free a prisoner** — a **communal pool** in the store. Any active player puts in **100 SE** at a time toward a prisoner's **500 SE** release; the pool (`players.release_pool`) **accumulates across market phases** and resets to 0 on release. At 500 the prisoner is freed immediately. `contribute_release(player, prisoner)` locks the prisoner row so two contributors can't both cross 500; freeing only *adds* an active player so it needs no win-check. *(Was a Virtues-only most-votes vote.)*

`GroupAction.tsx` is deleted and `startGroupAction`/`endGroupAction`/`resolveGroupAction` are gone. The old `rooms` columns (`eye_*`, `free_*`, `group_action_*`) + `resolve_group_action`/`count_active_camps` SQL are left **dormant** (unused). The Consultation Eye/freed banners are now inert (never set); a store freeing is **silent** — the player just reappears un-imprisoned next phase.

### Store & potions (migration 058+, in progress)

A `store` phase in the flow **outreach → store → store_summary → consultation** (migration 092 dropped the old `group_action` step). **On entry, every non-imprisoned, non-dead player gains +50 SE** (hospital players included; they bank it) via the idempotent `enter_store(room, ends_at)` RPC. Each active player privately spends their in-match **Soul Energy** on single-use potions that last one day cycle. Purchases are **secret** (kept in `player_secrets`, mutated only by SECURITY DEFINER RPCs, like role actions). Dead/imprisoned/hospitalised players can't shop. Bought via `buy_potion(player, potion, target?)` → `{ok, camp?, vices?, virtues?}`; the store UI reads its own armed state via `my_potions(player)`. The store also hosts the **Revealing Eye** potion and the **communal prison-release** funding (see "Camp abilities" above).

The six potions and their resolution timing (**updated migration 072**: combat potions now resolve when the **shop closes** — `resolve_store` — the same day, shown in the `store_summary` recap, NOT the next reflection as originally; the kill/protect/hospitalise machinery is duplicated into `resolve_store`):

| Potion | Cost | Effect | Resolves | Status |
|---|---|---|---|---|
| Kill | 300 | Kill a target | When the shop closes (`resolve_store`); protection-blockable | **DONE (2b/072)** |
| Hospitalise | 200 | Hospitalise a target 1 day | When the shop closes; protection-blockable | **DONE (2b/072)** |
| Protection | 200 | Shield self for a cycle | Blocks this shop's potion kills/hospitalise + sacrifices, AND the next reflection's Murder/Intoxication (migration 073 — `potion_protect` persists from the shop to the next role-action, then is cleared). NOT bomb detonations (unblockable). | **DONE (2b/072/073)** |
| Camp reveal | 200 | Reveal one player's camp | **Instant** on purchase (repeatable, SE-limited) | **DONE (2a)** |
| Revealing Eye | 150 | See how many Vices/Virtues are still active | **Instant** on purchase, **private to the buyer** (repeatable) | **DONE (092)** |
| Minigame multiplier (x2) | 60 | Double your minigame SE | **Next minigame** (`endMinigame` calls `consume_minigame_mult` → doubles those players' award) | **DONE (2a)** |
| Vote reveal | 100 | See who votes to imprison you | **This** day's consultation (the vote right after the store) | **DONE (2c)** |
| Iron Will | 200 | Your imprisonment vote counts **double** | **This** consultation (votes summed by weight in `resolve_consultation`/`consultation_tally`); cleared after. **Only buyable from round 2 on** (`day >= 2`); shown greyed + locked before then. | **DONE (075)** |

`player_secrets` carries the armed state: `potion_kill_target` / `potion_hosp_target` / `potion_protect` / `potion_minigame_mult` / `potion_vote_reveal` (all added in 058). Each resolver clears its own field after firing (nothing blanket-clears, so a potion armed in day N's store survives `new_day` into day N+1's reflection/minigame). The store UI (`Store.tsx`) mirrors the outreach timed + majority-advance pattern. `store` belongs to the **Action** TopBar segment (Outreach + Store + store_summary), and the whole Action phase shares the outreach background (a dedicated store/apothecary asset is a TODO). **All potions are wired**, plus the Revealing Eye + the communal prison-release funding (migration 092).

**Vote-reveal (2c, migration 060):** armed in day N's store, read **live during day N's consultation** via `my_voters(player)` — a gated RPC that returns the ids currently voting to imprison the caller, **only** if they armed the potion AND the room is in the `consultation` phase (during `group_action`, `player_secrets.vote` holds eye/free choices, which must not read as imprisonment votes). The `Consultation` voting + waiting screens poll it every 2s and show a private "voting to imprison you" panel (only the buyer sees it; votes stay anonymous to everyone else, and it updates live as votes change). Cleared in `resolve_consultation` (which only runs at the **final** resolution — a first-round tie goes through `start_revote`, so the potion survives into the re-vote). Migration 060 also rebased schema.sql's `resolve_consultation` from pre-056 to the live 056 logic + the clear.

**Combat-potion rules (2b, migration 059):** decided with Matthijs — **Protection is self-only**; a player may buy **one of each** combat type per day (Kill + Hospitalise + Protection independently), re-buying an armed type is rejected. They resolve in the **next** day's `resolve_role_action`, folded into the existing kill → protect → hospitalise pass: potion kills/hospitalises are added to `v_dead`/`v_hospital` (protect-checked), potion protects add the buyer to `v_protected`. A combat potion fires **only if the buyer is still alive** (not dead) at resolution — a jailed buyer's potion still fires, a dead buyer's fizzles; the target must not be already-dead. Potion kills feed Murder-succession + win checks + the anonymous "killed" event exactly like a role kill (no `murder_kills`/badge credit). `resolve_role_action` clears the three combat fields after they fire (leaving `potion_minigame_mult`/`potion_vote_reveal` for their own resolvers). **schema.sql's `resolve_role_action` was still the pre-056 version; migration 059 brought it up to the live 056 logic + the potion bits, so it's now mirrored.**

### Accounts, profiles, friends, stats & badges

Real accounts exist alongside guest play (Supabase Auth, email + password, **email confirmation ON**). **Joining a room stays guest-only; creating a room requires an account.** A logged-in player's `players.user_id` links their per-game row to their account.

- **Auth UI:** `AuthControl` (top-right of home) → `AuthModal` (login/sign-up). `useAuth()` hook tracks the session + profile. Login is by email (username login deliberately not built — would expose emails).
- **Profile (`/profile`):** a customizable **character** avatar (see "Character avatars" below), username, stats, and badges. Photo upload was **removed** (migration 091); the old `profiles.avatar_url` column + `avatars` Storage bucket are left dormant. Favorite role was **removed** (its `profiles.favorite_role` column is left unused).
- **Character avatars (migration 091, replaces photo upload):** each account customizes a stylized **shoulder-up portrait** — male/female build, skin tone, hairstyle, hair colour, **facial hair** (mustache / beard / both) + its colour, eye colour, **facial expression** (neutral/happy/angry/sad/scared), and **outfit (collar) colour** — stored as `profiles.appearance` (jsonb; the column is `appearance`, not `character`, because `character` is a reserved SQL keyword). The avatar is **pure inline SVG** drawn parametrically by `CharacterAvatar` (`src/components/CharacterAvatar.tsx`): the head, eyes, hair and collar are vector shapes recoloured from the config, so **any colour/style combination is free and there are no image assets**. Two framings from the same SVG: **`variant="badge"`** (default) = a round head-and-shoulders portrait on a **warm-brown radial backdrop** (the game's home-bg/panel brown `#43301e`→`#241710`, darkened at the edges so every skin tone + hair colour still separates from it) — hub HUD, lobby rows, profile, friends, leaderboard, invite picker; **`variant="full"`** = the same bust in a rounded panel, no backdrop (the profile character widget — clicking it opens the editor). In-game role heads (`RoleIcon`) are unaffected. `src/lib/character.ts` is the single source of truth — `GENDERS`, `EXPRESSIONS`, `SKIN_TONES`, `HAIRSTYLES` (`none`/`short`/`long`/`ponytail`/`bun`/`curly`, each mapped to SVG paths in the avatar), `HAIR_COLORS`, `FACIAL_HAIR` (`none`/`mustache`/`beard`/`both` — drawn over the lower face, tinted by `facialHairColor` from the hair palette), `EYE_COLORS` (incl. a sinister **red**), `OUTFIT_COLORS`, `DEFAULT_CHARACTER`, and `normalizeCharacter` (coerces legacy/missing fields — incl. the **old outfit-piece fields** — to defaults; `gender` defaults to male, `expression` to neutral). **Gender drives the build** via a `TRAITS` map in `CharacterAvatar`: **male** = wider jaw + wider neck + bigger traps; **female** = bigger eyes with lashes + a softer, slimmer jaw/neck/shoulders. **Expression** drives a separate `EXPR` map that reshapes the **brows + eye openness + mouth** (neutral / happy / angry / sad / scared). The editor is `CharacterCreator` (its own modal, opened by clicking the character widget on `/profile`; the banner opens a **separate** banner-colours modal — `ColorCustomizer`); saved via `saveCharacter` (`lib/profile.ts`, plain self-update RLS — no RPC). The customizer shows **Body (male/female) · Skin tone · Hairstyle · Hair colour · Facial hair (+ colour) · Eye colour · Expression · Outfit colour**. The **previous PNG-layer pipeline was removed**: `public/characters/*` (gender bases, hair, outfit PNGs), the canvas-multiply tinting, and the SVG placeholder are all gone. **Random by default:** accounts that haven't customized yet (`appearance` is null) get a **deterministic random character keyed by their account id** — `randomCharacter(seed)` + `withDefaultCharacter(profile)` in `character.ts`, applied in every loader that reads a profile (`auth.getMyProfile`, `friends.searchUsers`/`getFriendData`, `leaderboard`, `Lobby`, `/profile/[id]`). It's stable across reloads and viewers with **nothing persisted** (no migration/backfill); the moment a player customizes, `saveCharacter` writes their `appearance` and overrides it. (Expression is weighted toward neutral and the random hair is never bald, so defaults look friendly.) A genuinely missing character still falls back to initials. `Banner` takes a `character` prop (was `avatarUrl`); `leaderboard_top_wins` returns `appearance` jsonb (was `avatar_url`).
- **Stats:** computed from `game_results` (one row per account per finished game, written by the host on game-over via `lib/stats.ts` `recordGameResults`, marking a win for the whole winning camp incl. dead/imprisoned). Profile shows total games, wins, win rate, wins-per-role, and the last 5 games. `ProfileStats` is shared by self + friend profiles.
- **Friends (`/friends`):** username search → request → accept (per-user RLS: only the addressee can accept; either party can delete). Friends list renders each friend's **`Banner` at uniform full width** (`fullWidth` prop — stretches to the column so all banners are the same length; avatar + name + featured badges stay left-packed so the right side is free) with a compact **gamepad-icon + number chip overlaid on the top-right corner** showing games played together (shared `game_results.room_id`); same in the hub Friends tab + `/friends`. `/profile/[id]` is a **read-only render of the same `ProfileDashboard`** as your own profile (`editable={false}`). It now uses the **same two-column identity layout** as your own profile — banner (top) + the **same `FeaturedBadges` widget (read-only)** (bottom) on the LEFT, the player's **character widget on the RIGHT** (`CharacterAvatar variant="full"`, read-only) — so a visited profile looks identical to your own, just with nothing editable. `FeaturedBadges` takes a `readOnly` prop: the card stops being a button (no picker / hover / brush) and empty slots show a plain dashed circle instead of "+ Add badge"; the gold heading + big `h-20` medallions are unchanged. The read-only banner is `size="lg"` with the **level inside the 9-pointed star** (`levelStar` + `level` + `levelProgress` → star + progress bar, no exact XP numbers); their level comes from the public `get_account_xp` RPC (migration 088) since `account_economy` is otherwise read-own. Below the identity row: stats + earned badges, no customize affordances.
- **Badges (`lib/badges.ts`):** an 83-badge catalog across five tiers (Divine → Noble → Primal → Verdant → Earthen), incl. a 60-badge per-role win matrix (1/5/15/40/100 wins → one threshold per tier) and totals/specials. **Medallions (`BadgesShowcase.tsx` `Medallion`, now exported) use painted per-tier frame art** (`public/badge-frame-<tier>.png`, AI art with the black background edge-flood-filled to transparency) — the old procedural SVG `Decor` is gone. Divine/Noble/Primal frames are **punched** (transparent centre): the icon is drawn *behind* the frame so the ring + cardinal gems sit in front, with each gem's gold setting preserved; Verdant/Earthen keep a solid frame with the icon on top. A per-tier ellipse `FRAME_WINDOW` + a `PUNCHED` flag drive the layout. **Role badges** show that role's tier-tinted character icon (`public/badge-icons/<role>-<tier>.png`, 12 roles × 5 tiers — a grey head colorized to the tier hue, on a dark recessed disc); **glyph badges** (no character art) show an inline icon on a per-tier `GLYPH_COIN` coin — dark+gold for most tiers, **white+gold (Divine)** and **purple+gold (Noble)** to match those bright frames. ### Moderation & safety (public play)

Three layers, all in place:
- **Tiered text filter** (`lib/profanity.ts`) — general profanity is censored (still sends); slurs are hard-blocked via `cleanForSend()` on every chat send path + name validation. Defeats leetspeak, Unicode/homoglyph/zero-width tricks, and spaced-out letters.
- **Block** (`lib/blocks.ts` + `BlockedStrip`) — per-device, per-room. Hides a player's chat from you everywhere + drops them from your outreach partner list. Block buttons in the lobby + on chat messages + the outreach thread header; unblock via the BlockedStrip (or lobby). Pure client-side display filter — never affects game state. Works for guests + accounts.
- **Report + auto-mute** (`lib/reports.ts` + `report_player` RPC) — Report buttons sit next to Block (lobby, chat messages, outreach header). After **3 distinct** reporters in a game, the reported player is **auto-muted** (`players.muted` → realtime → their composers disable with "You've been muted for this game"). Mute is enforced client-side in all four composers (consultation/dead/camp/DM), consistent with the MVP threat model; full server-side enforcement folds into the pending RLS tightening. Every report is logged to the locked `reports` table for **manual review in the Supabase dashboard** (e.g. `select reported_user_id, count(distinct reporter_id) from reports group by 1 order by 2 desc`).

### Ranked ladder (migration 051 — `lib/ranked.ts`)
- **5 tiers** (Earthen < Verdant < Primal < Noble < Divine) × **3 divisions** (Division 1 is highest), **100 points** per division. Reuses the badge tier art.
- **Points:** win **+20**, loss **−15**, adjusted **±2.5 per 1-player gap** between Vices and Virtues *remaining* (alive & not imprisoned) at game end — a dominant win / heavier loss moves rank more.
- **Promotion** = winning **while at 100**; **demotion** = losing **while at 0** (no silent auto-move). A promotion lands at **0** of the higher division; a demotion lands at **75** of the lower. Apex = Divine I @100; floor = Earthen III @0.
- `rooms.is_ranked` + `account_ranked` (world-readable) + `account_ranked_rewards` ledger; `apply_ranked_results(p_room_id, p_results)` RPC (host-side, idempotent per game) is called at game-over in `stats.ts` (which computes the camp diff from revealed roles + final player states, only when `rooms.is_ranked`). `RankPanel.tsx` shows the player's rank. **Self-created rooms are always casual** — ranked games come only from the `/ranked` matchmaking queue (the lobby's old Casual/Ranked toggle was removed; `setRoomRanked` in `room.ts` is now unused, and `rooms.is_ranked` defaults to `false`).

### Phase-transition reliability fix (`app/room/[code]/page.tsx` + `lib/useMajorityAdvance.ts`)
Phase changes are written server-side, but a missed realtime event could leave the host stuck (Start → "Starting…"; the game-overview Proceed gate showing "1/1" with no advance). Added a **3 s full-state poll fallback** that re-pulls **room AND players** (`resync`) so transitions always land even if a live event is dropped (realtime stays the fast path). It must refresh players too, not just the room: the majority-continue gate (e.g. the game-overview Proceed) advances only once the host's client sees a majority of players `ready`, so a single dropped player-`ready` UPDATE would otherwise leave **everyone proceeded but the game never starting** — the poll was room-only until this was fixed. Also added `is_ranked` to `PUBLIC_ROOM_COLS`.

**Majority-advance arming (`useMajorityAdvance`):** the gate only advances once `resetSeen` is armed, which originally required *observing the phase's ready-reset land* (everyone not-ready). That permanently stuck any client whose **first** view of the phase already showed players `ready` — a refresh, a reconnect, or a transition race — and because the **host** drives the advance, if the host's client never armed, nobody moved (classic repro: solo host on game-overview, "1/1" ready, no countdown, frozen). Fix: also arm when `phase_ends_at` is **null** (no pending deadline → nothing to prematurely advance against, so the raw ready flags are safe to trust; the host still only advances after setting a fresh 10 s countdown on a real majority). `game_overview` always enters with `phase_ends_at = null`, so it now arms regardless of how the client arrived. Phases that inherit a stale non-null deadline still fall back to the observe-all-not-ready guard, so the original premature-advance protection is unchanged.

Root-cause check if it recurs: ensure `rooms` is in the realtime publication (`select tablename from pg_publication_tables where pubname='supabase_realtime'`; fix with `alter publication supabase_realtime add table rooms;`).

## Database schema (current — see `db/schema.sql` for full definition)

**rooms**
`id, code(unique), status(lobby|in_game|ended), is_public(public lobby flag, default false/Private), phase, phase_ends_at, day, outreach_enabled(legacy — outreach is now mandatory), last_imprisoned_player, vote_reveal, envy_swap_a/b, torment_target, pending_murder_death, revote_candidates(jsonb), recent_successor_id, last_events(jsonb), group_action_result(legacy/unused), group_action_freed_id, eye_revealed, eye_uses_left, free_uses_left, role_pool(jsonb), next_room_code(re-queue target lobby), minigame_clue(jsonb — shared most-read-player clue), vengeance_imprisoners(jsonb — SECRET; ids of players who voted to jail Vengeance, for her revenge; migration 056), role_assign_mode('random'|'choose', migration 063), role_config(jsonb — host per-tier config for random mode, lobby batch), pride_target(SECRET — player Pride blocked from this minigame, migration 066), love_tiebreak(SECRET — the Love who armed this day's consultation tie-break; cleared each new day, migration 067), bombs(jsonb — SECRET; Fanaticism's live bombs [{id,holder,since,pass_to}]; never in PUBLIC_ROOM_COLS, migration 068), bombs_planted(lifetime bomb count, cap 2, migration 068), kill_log(jsonb — SECRET during play; [{killer,victim,day}] for the game-over overview; read only via get_kill_log once ended, migration 074), created_at`

Where `phase` is one of: `lobby | game_overview | role_select | role_overview | lore_intro | role_reveal | role_action | murder_succession | event_summary | minigame | result | outreach | store | group_action | consultation | new_day | vice_victory_intro | virtue_victory_intro | game_over`.

**players**
`id, room_id, user_id(→auth.users, NULL for guests), name, is_host, connected, role, ready, minigame_score, minigame_submitted_at, soul_energy, vote, in_prison, dead, in_hospital, acted_this_day, pending_action(kill|protect|intox|vengeance_guess|sacrifice|envy_swap|torment|worshipper_guess|seeker_guess), pending_target(single id, or a JSON array of ids for sacrifice), murder_kills, muted(auto-muted after repeated reports), created_at`

**reports** — `id, room_id(→rooms cascade), reporter_id, reported_id, reported_user_id(account, if any), reason, created_at`, unique(room_id, reporter_id, reported_id). RLS locked (no client policies) — only the `report_player()` SECURITY DEFINER RPC writes it; **review via the Supabase dashboard**. The RPC auto-mutes (sets `players.muted`) after 3 distinct reporters in a game.

**messages** — `room_id, camp, sender_id, text, created_at` (anonymous camp chat — **legacy**: Worshipper/Seeker were reworked in migration 056 and no longer broadcast, so nothing writes here now)

**player_notices** — `id, room_id(→rooms cascade), recipient_id(→players cascade), text, created_at`. Private per-player notices (e.g. a Worshipper/Seeker revealing themselves). **Locked** (no RLS) — written only by `reveal_self`, read via `get_my_secrets`; not in realtime. The client (`PlayerNotices`) shows un-dismissed ones and remembers dismissals in localStorage. (Migration 056.)

**dm_messages** — `room_id, sender_id, recipient_id, day, text, created_at` (1-on-1 outreach chat, filtered to current day)

**consultation_messages** — `room_id, sender_id, day, text, created_at` (public consultation chat, per-day)

**dead_messages** — `room_id, sender_id, text, created_at` (dead-only side channel, no day filter — spans the game)

**profiles** — `id(→auth.users), username(unique, case-insensitive), favorite_role(unused), avatar_url, featured_badges(text[] — up to 2 showcased badge ids), name_color, banner_color(equipped cosmetic-color tier ids or null — migration 080), created_at`. An `on_auth_user_created` trigger creates the row from sign-up metadata. RLS: world-readable, write-your-own. The `leaderboard_top_wins(p_limit)` SECURITY DEFINER function aggregates `game_results` wins joined to `profiles` for the leaderboard.

**game_results** — `id, user_id(→auth.users), room_id(no FK — survives room cleanup), role, camp, won, created_at`. One row per account per finished game. RLS: open (MVP).

**user_achievements** — `(user_id, key)` PK, `created_at`. Event/claim badge keys. RLS: world-readable, insert-your-own; plus a SECURITY DEFINER `grant_achievements(jsonb)` RPC the host uses to award keys to any player.

**friendships** — `id, requester_id, addressee_id, status(pending|accepted), created_at`, unique(requester,addressee). RLS: see-your-own; insert as requester; only addressee updates (accept); either party deletes.

**account_economy** — `user_id(PK→auth.users), life_experience(=LP), mano, xp, unopened_shards, last_daily_shard_date, last_first_win_date, daily_win_count`. `daily_win_count` (migration 077) counts today's wins (0–3) on `last_first_win_date` — each of the first 3 mints a Soul Fragment. Seeded by `handle_new_user`. **Locked** (no client write policy) — mutated only by the economy RPCs.

**account_role_unlocks** — `(user_id, role)` owned roles. Locked; written by `open_soul_shard`/`unlock_role`. All 12 roles are treated as unlocked by default in code.

**account_color_unlocks** — `(user_id, color)` owned cosmetic colors/banners. Holds Mano shop colors (migration 081, `buy_color`), the Founder pack's `pioneer`/`founder` (082, `buy_founder_pack`), and the season pass's `spirit`/`firstsouls` (083, `claim_season_tier`). **World-readable** (so other players' equipped cosmetics resolve in-game). Equipped via `set_cosmetic_color` onto `profiles.name_color` / `banner_color`.

**account_season** — `(user_id, start_xp, premium, claimed_free[], claimed_premium[])` season-pass progress (migration 083). `start_xp` snapshots account xp at launch → season XP = `xp − start_xp`, tier = `floor(season_xp/300)` capped 50. Locked (RLS read-own); written by `get_season`/`buy_season_premium`/`claim_season_tier`.

**account_match_rewards** — `(user_id, room_id)` idempotency ledger for `grant_match_rewards` (per-match XP/LP + first-win shard, granted once).

**account_ranked** — `user_id(PK), tier_index(0-4), division(1-3), points(numeric), games, wins`. **World-readable** (for rank display); written only by `apply_ranked_results`.

**account_ranked_rewards** — `(user_id, room_id)` idempotency ledger for `apply_ranked_results`.

**account_role_config** — `user_id(PK), config(jsonb)` — preferred role per side per tier. **Normal per-user RLS** (read/insert/update your own); the player edits it freely.

**ranked_queue** — `user_id(PK), mode('3v3'|'6v6'), side, name, status, room_code, joined_at`. Read-own RLS (sides stay hidden). Written by the queue RPCs (`join/leave_ranked_queue`, `ranked_matchmake`/`ranked_form_match`).

`rooms` also gained **`is_ranked`** (migration 051).

RLS: the six game tables (`rooms`, `players`, `messages`, `dm_messages`, `consultation_messages`, `dead_messages`) + `game_results` use open policies (MVP). `profiles`, `friendships`, `user_achievements` use real per-user policies. Realtime publication includes the game/chat tables + `profiles` + `friendships`.

## Key design decisions (rationale, not just behavior)

- **Soul Energy formula simplified** from `Y × M` (M = 1000/scoring-players) to `100 × 0.93^(rank-1)` so a rank is worth the same regardless of player count.
- **Wrong-guess penalty in minigame**: any explicit V/V mismatch zeroes both the raw score AND the SE awarded for that round. Implemented in two places (`computeScore` short-circuits to 0; `rankPlayers` awards 0 SE when raw score ≤ 0). Encourages players to leave uncertain rows as "?".
- **Guests + accounts coexist** — guests still use `localStorage` (`vv_player_id`/`vv_player_name`) and each join makes a new player row. Accounts (Supabase Auth) are required only to **create** a room; a logged-in player's `players.user_id` links the row so stats/badges accrue. Login is email-only on purpose (username login would need to expose emails).
- **Lobbies auto-expire after 10 minutes** — a room never started within 10 min of creation is deleted and everyone in it is bounced to the start screen, and matchmaking skips lobbies past that mark. Fixes AFK-host lobbies piling up and "Find Public Session" dropping players into rooms that never begin. Enforced server-side (pg_cron every minute + a freshness guard in `find_or_create_public_room`) with a client self-heal (the lobby countdown calls `expire_stale_lobbies()` at 0) so it's immediate. Timed from creation regardless of activity, and applies to private/code lobbies too — an in-person group has 10 min to hit Start. The cutoff lives in both `db/055_lobby_expiry.sql` and `LOBBY_EXPIRY_MINUTES` (keep them in sync).
- **Camp-restricted group action** — the old democratic Eye/Free/Skip vote was split into a Vice-only Revealing Eye and a Virtue-only free-a-prisoner, decided simultaneously, each once per game. No vote counts are shown in-phase because the eligible-voter count per camp would leak camp sizes. The `group_action_target` follow-up phase was removed (the prisoner choice folds into the Virtue ballot).
- **Badges** — derived badges (games/wins/per-role/account-age) are computed live from `game_results` + `profiles`; event/claim badges are recorded keys in `user_achievements`. Self-detectable events (minigame 1st, no-"?" minigame) are written by the player's own client; resolution-level events (Murder kills, kill-teammate, Justice protect, Envy escape, murdered-while-hospitalised, freed-from-prison) are granted by the **host** via the `grant_achievements` SECURITY DEFINER RPC (since RLS otherwise only lets a user write their own). The RPC bypasses RLS and is callable by anyone — an accepted MVP trust trade-off, on the pre-launch tightening list.
- **Action queue resolution** in `resolve_role_action`: collect protects first → apply kills (skipping protected) → apply hospitalizations (skipping protected and just-killed) → apply kill + win check. Sacrifice contributes to deaths from both sides (protect can spare either side). Vengeance hospital isn't blocked by protect. **(Murder succession removed in migration 061 — a killed Murder just dies.)**
- **Extra lives (migration 066)** — `player_secrets.extra_lives` is a stored buffer (Determination buys 100 SE/stackable, Generosity grants for 200, Wrath earns by relinquishing a follower in migration 067). In `resolve_role_action`, AFTER all kills/hospitalisations are tallied but BEFORE kill-counting/achievements/win check, each player in the dead set with an extra life is pulled out (−1 life) — so an absorbed kill counts as if it never happened; then the same for the hospital set. Consultation **instant-Sacrifice bypasses extra lives** (it bypasses Justice protect too — a mutual-death pact shouldn't be cheated by a stored life). The owner sees their count via `get_my_secrets` → a ♥N chip in the TopBar.
- **Gambling routes through the normal queue** — `gambling_roll` (migration 078) rolls one die server-side; the face decides the outcome, and the kill/hospitalise faces reuse existing resolution by writing `pending_action='kill'`/`'intox'` (self for roll 1), so protect + extra lives apply with no special path. Faces 4/6 defer the target to `gambling_pick_target`; the minigame faces flip `minigame_no_score` (roll 2) / `potion_minigame_mult` (roll 3). **Pride** uses `rooms.pride_target` read by `submit_minigame_guesses` to zero that player's round, and a `player_notices` reveal (cost 50 since migration 078). **Diligence** is immune to the wrong-tag zero inside `submit_minigame_guesses`, which also stores `minigame_correct` for the result-screen paid count.
- **Wrath/Love conversion is a QUEUED action resolved at the end of role-action (migration 071; was instant in 067)** — `convert_player` only sets `pending_action='convert'` + charges 200 SE; `resolve_role_action` applies the role flip (`player_secrets.role` → `vice_worshipper`/`virtue_seeker`) **after** the turn's other actions resolved (so the target's own ability **this** turn still fires) and **before** the pending-action clear + win check (a conversion flips a camp, which can decide the game). It's evaluated against a **snapshot** of camps/tiers captured before any conversion lands, so two converts on the same target can't chain (each is judged on the pre-conversion roles). **It's a gamble** (200 SE, migrations 070-071) — it lands only on a **still-alive, non-S-tier** role of the wanted camp (only a Virtue can be corrupted / only a Vice turned, and **all S-tier roles — Murder, Wrath, Empathy, Love — are immune**, which also makes Wrath and Love immune to each other), but the 200 SE is spent on a whiff either way. The **caster** gets a notice with the outcome ("took hold" / "resisted") since there's no instant result; the **converted player** learns of the camp switch via a prominent centered `RoleChangePopup` (client-detects their own role changing — conversion is the only mid-game role change, gated to the two conversion roles so the initial deal/role-select don't trigger it). The conversion is never revealed publicly (no event). Wrath's converts set `follower_of` (binding them to that Wrath); Love's clear it. **`relinquish_follower`** consumes a follower (instant death, bypassing their own extra lives like a Sacrifice does) to mint a Wrath **extra life** (the 066 buffer) — so Wrath turns Virtues into a renewable life supply. **Love's tie-break** (`love_tiebreak`, one day) only breaks a tie Love actually **voted into** — it biases a deadlock toward her pick rather than being a free imprisonment; it's mirrored in `consultation_tally` so the host's re-vote gate and the result screen agree with `resolve_consultation`. `love_tiebreak` stays server-only (sending it would out Love).
- **Fanaticism bombs live on `rooms.bombs` (jsonb, SECRET) and move in `resolve_role_action` (migration 068)** — bombs are NOT in PUBLIC_ROOM_COLS, so the array never reaches a browser; the current holder learns they hold one only via `get_my_secrets` (`bomb_must_pass`), and only Fanaticism can pay 100 SE (`bomb_carriers`) to see the holders. Each bomb carries `since` (the day its current holder received it); the pass step at the end of `resolve_role_action` moves only bombs with `since < today` (so a freshly-received bomb sits one full day before its holder must pass), to the holder's chosen `pass_to` if still active else a **random** active player — and a bomb whose holder went inactive always relocates, so bombs never strand on a dead/jailed player. **Detonation is deliberately blind** — the consultation detonate UI (`my_bombs`) shows only bomb ids + alive-flags, never the holder, so the 100-SE scout has real value and a bomb that drifted onto a teammate kills them; Fanaticism gets a private `player_notice` telling them who died. Detonation is an **instant consultation kill** (`detonate_bomb`) that bypasses protection/extra-lives exactly like instant Sacrifice, because those are reflection-phase shields. The 2-bomb lifetime cap uses `rooms.bombs_planted` (a counter), since detonated bombs leave the array and couldn't otherwise be counted.
- **Envy swap is purely visual** — `displayedName()` swaps names; clicking a row stores the real underlying id (the deceived outcome). **The swap is hidden from the swap participants themselves** (Envy + the victim see real names everywhere via the optional `viewerId` arg) so the victim can't catch the swap by seeing their own name on someone else's row.
- **Host orchestrates phase advances + majority-continue.** Every interactive phase supports majority-continue (`lib/useMajorityAdvance.ts`, `CONTINUE_SECONDS = 10`): when a majority of the electorate presses Continue/Proceed/Done — or, in timed phases, finishes early — the **host's** client sets `phase_ends_at = now + 10s` (a visible countdown every client sees via realtime) and advances when it elapses. Timed phases (role_action / minigame / outreach) just *shorten* their existing timer to 10s (then advance at `endsAt + 1.5s` grace so stragglers' auto-submit/ready writes land); host-gated screens (game_overview, role_reveal, event_summary, result, consultation result, victory intros) gain a Continue button for **all** players plus the 10s countdown. The host can still "Skip" instantly via TopBar (calls the same transition fns — no conflict, since the phase change unmounts the component). The hook **requires the ready-majority to advance** (not merely an elapsed deadline) and only renders its countdown when a majority has started one, so a `phase_ends_at` inherited from a prior sub-phase can never auto-skip a screen. **Excluded by design:** cinematics (lore_intro, new_day — fixed auto-timers) and the secret-ballot phases (group_action + consultation **voting**), which need *all* eligible votes for an accurate tally and can't surface counts without leaking camp sizes — they keep all-voted + timer. A first-round consultation **tie** still needs an explicit host re-vote decision. Ready is reset on entry to every majority-continue phase (`startRoleAction`/`startMinigame`(via `endMinigame`)/`startOutreach`/`startGroupAction`/etc.); victory intros reset it client-side on mount (host) since they're reached from SQL `resolve_*` fns that don't.
- **Murder succession removed (migration 061)** — a killed Murder simply dies; there is no hand-off to a Vice successor. The `murder_succession` phase, `MurderSuccession.tsx`, and the `choose_murder_successor` / `eligible_successors` RPCs (+ `rooms.pending_murder_death` / `recent_successor_id`) are now **unreachable dead code**, left in place. The Murder+1 endgame win is unchanged.
- **Outreach scope simplification:** any active or imprisoned player can chat with any other (dead/hospital see passive screens with the dead chat). After clicking Done you stay on the partner list / threads (no waiting screen) so you can still see and send messages until the phase ends.
- **DM history resets each day** so Empathy's voter reveal can't be cross-referenced with stale DMs about yesterday's votes. Messages stay in the DB; the Outreach component filters by `room.day`.
- **Anonymous role-action deaths**: EventSummary shows the dead player's name + first-letter avatar in neutral brown, but no role / camp / Fallen breakdown. Roles are only revealed publicly at `game_over`.
- **Group action uses are decremented only when the action fires** (Eye fired; a prisoner was actually freed). A tie / "don't free" lead frees no one and consumes no use.
- **Reset-seen guard for phases entered after a vote-clearing transition** (Consultation, GroupAction): the host's auto-advance only fires after we've observed `vote=null` on every active player. Without this, the previous phase's votes still appear set in the client's local state and the host auto-advances within ~1s.
- **Sync animations via `phase_ends_at`**: the LoreIntro zoom and victory intro fade-to-black are anchored to the absolute db timestamp, not to a local setTimeout from when the client received the realtime update. Otherwise slow clients miss the climax.
- **Transparent PNG via plain `<img>`**: Tailwind v4 compiles `scale-*` to CSS-variable updates which don't reliably trigger transform transitions, and Next.js's `<Image>` optimiser repackaged transparent PNGs in a way that left a visible checker pattern. The logo on home + lobby uses plain `<img>` (with a `?v=N` cache-buster) to dodge both.
- **Outreach is mandatory** — the lobby toggle was removed; Result and the host Skip always advance to outreach (`outreach_enabled` is now a dead column).
- **Viewport-pinned backgrounds** — the `cover` phase backgrounds zoomed in on tall/scrolling pages because `background-size:cover` scaled to the element's full height. Fixed by painting the image on a `position:fixed; inset:0; z-index:-1` `::before` (viewport-sized) with `isolation:isolate` on the host so the layer shows above the element's solid colour. **Do NOT put `position:relative` on these classes** — it overrides a `fixed` utility on overlays that reuse the class (this broke the rules overlay once). In-game screens use `pt-16` so content clears the (now taller, labelled) fixed TopBar.
- **Sounds are synthesized, not files** — see `lib/sound.ts`. One shared `AudioContext`, unlocked by the first click, reused for click/whoosh/victory/prison-door. Web Audio scheduled nodes keep playing after a component unmounts, so victory songs carry into the scoreboard.
- **Auth emails live in the Supabase dashboard**, not the repo — only the banner image (`email-banner-v3.png`) is in the repo. Gold buttons must be "bulletproof" (bg on a `<td>`, Gmail strips `<a>` bg); use `bgcolor` attrs + `font-size:0` image cell + no `border-radius` to avoid white edges on mobile; bake the banner as one `<img>` (no CSS bg images in email).
- **`grant_achievements` host RPC** — resolution-level event badges are granted by the host to any player via a SECURITY DEFINER RPC (RLS otherwise only allows writing your own). Record game results BEFORE flipping to `game_over` so the "new badges this game" diff is accurate.
- **Painted badge frames are punched, not layered** — Divine/Noble/Primal frame PNGs have a transparent centre hole, and the icon is drawn *behind* the frame so the ring + inward cardinal gems render in front of (and slightly over) the icon. A clean elliptical hole would clip the gems' inward-protruding gold settings, so the punch preserves warm-gold pixels near the cardinal axes that connect to the ring (drops floating crystal "wisps" via the same connectivity check). Verdant/Earthen keep a solid frame with the icon on top. The per-tier hole + window numbers are baked into the PNGs by a reusable PIL script and mirrored by `FRAME_WINDOW`/`PUNCHED` in `BadgesShowcase.tsx`. Icons are pre-tinted PNGs (not CSS-tinted) for exact per-tier/per-camp colour.
- **Re-queue = opt-in new lobby, not a same-room reset** — the end-screen "Play again" creates a *fresh* room; the first re-queuer (must be an account — room creation needs one) records its code on the finished room's `next_room_code` (atomic claim if still null, so simultaneous taps converge on one lobby), and everyone else who taps joins that code. Avoids resetting the finished room's locked `player_secrets`/state and lets non-participants stay on the results screen.

## Bug test checklist

Walk through whenever significant gameplay changes ship. Run on at least two clients (host + non-host); ideally one phone + one browser.

### Pre-game
- Home screen logo loads cleanly (no white box, no checker pattern). Bust the browser cache on logo file changes.
- "How to play" opens the rules guide; every role's expandable description renders.
- "Join the Discord" opens the invite in a new tab.
- Name persistence: enter a name, refresh, name still there.
- Join with a wrong code → error message; join with a right code → lobby.

### Lobby & game start
- Multiple players show up live as they join (account players show their avatar + featured badges; guests show an initial).
- Host can kick; players can leave.
- Start Game → Game Overview ("The game begins": walkthrough slideshow + this game's role list) → Lore Intro → Role Reveal flow. (No outreach toggle — outreach is always on.)
- Lore Intro: the `abyss_flight` cutscene runs on every client (synced via `phase_ends_at`), ends on black, advances at t=3.5s. **Test on slow network too — everyone should land on the next phase together under the blackout.**

### Role Reveal
- Each player sees the right role card (image + description).
- All-ready gate advances to role_action.

### Role Action (30s)
- Each ability targets correctly; SE is deducted; `acted_this_day` flips.
- Murder kill / Justice protect interactions.
- Sacrifice queued vs instant.
- Vice Worshipper / Virtue Seeker camp chat appears for the right camp only.
- Envy swap: the **victim does NOT see their own name on anyone else's row** (Envy + victim both see real names; only third parties see swapped names).
- Envy swap voting still routes to the real id.

### Event Summary (after role_action)
- Killed events: real name + first letter + neutral brown avatar; **no role or camp shown**.
- Hospitalised events: real name + first letter + neutral brown avatar.
- Host has the only Continue button; others wait.

### Minigame (95s)
- Every untagged row shows the "?" pill visually selected by default.
- Score: any wrong V/V tag → 0 raw score → 0 SE awarded (regardless of rank).
- Score: all-unknowns or all-correct → positive score → standard rank-based SE.
- Torment target sees **scrambled names** (no row keeps its real name, shuffle is stable across re-renders within the round, completely different per game/day).
- Imprisoned / hospital / dead see passive screen; dead see the dead chat embedded.

### Result (scoreboard)
- Ranked list shows only players who actually played.
- Non-scoring players (dead/prison/hospital) see the explainer banner.
- No Fallen section / role reveal here.
- Host-only Continue.

### Outreach (120s)
- DM history starts EMPTY each new day (previous days hidden).
- Imprisoned players appear in the partner list and can chat.
- Done button: clicking marks ready but does NOT switch to a waiting screen — partner list / threads stay live, messages keep arriving and can still be sent.
- Cross-chat notification: receive a DM from someone other than the currently open thread → banner appears at the top, tap to switch.
- Back arrow in the thread view is visible (not hidden under the TopBar).

### Group action (Vice Eye + Virtue free-a-prisoner, simultaneous)
- Vices see the Eye Yes/No ballot only while `eye_uses_left > 0`; Virtues see the free-a-prisoner ballot only with prisoners present and `free_uses_left > 0`.
- Players with no available action (wrong camp / used up / no prisoners / dead-prison-hospital) see "Nothing to decide" and wait.
- **No vote counts are shown** anywhere in this phase (would leak camp sizes).
- Eye fires only if Yes > No; freeing is most-votes-wins (tie / "don't free" → nobody freed).
- Both can fire the same round → both banners show in consultation (Eye counts to everyone; freed player).
- Use counts decrement ONLY when an action actually fires; each is once per game.
- **No public chat on this screen** (removed): the team ability is a secret simultaneous camp decision, so a chat would let players discuss camp-only abilities and leak their camp. Dead players keep their dead-only chat.
- **Important sync check:** test multiple consecutive days — the phase should NOT auto-skip on day 2+ (resetSeen guard); and when both abilities are exhausted it should advance promptly (no 60s dead wait).

### Consultation (95s)
- Vote list excludes self.
- Skip vote button is brown.
- Tied vote → host can trigger one re-vote.
- Truthfulness reveal embed works for the imprisoned target.
- Sacrifice instant kill in consultation.
- Group-action banner from earlier still visible at top.
- Dead players see the public chat + dead chat + the result fall-through; can't vote.
- Public chat persists across the sub-screens (per-day filter).

### Death / win conditions
- Kill → Fallen banner does NOT appear mid-game; role only revealed at game_over.
- Dead players see the dead chat on every passive screen across phases.
- Murder + 1 other active player → instant Vice win.
- Camp elimination → corresponding victory intro → game_over.

### Victory intros + Game Over
- Vice victory → ruined-town image + "Wrath's belief is proven true…" text fades in after 1s; host clicks Continue.
- Virtue victory → sunny-city image + "Unity prevails…" text fades in after 1s; host clicks Continue.
- Both animations sync on all clients (anchored to phase_ends_at).
- GameOver scoreboard uses the matching victory image as background.

## Gotchas learned the hard way

- **Stale ready flags / votes** ended phases instantly when realtime delivered the phase change before the clearing-write landed. Fixed with `resetSeen` guards in Minigame, RoleAction, Outreach, Consultation, GroupAction. **Apply the same pattern any time a new phase is entered with vote/ready clearing.**
- **Dead/imprisoned host couldn't advance consultation** because the dead-screen early return blocked their Continue button. Fixed by only short-circuiting dead/prison/hospital screens *while voting is in progress*; once all voted, everyone falls through to the result + (host) Continue.
- **HTML entities** (`&mdash;` etc.) only render inside JSX text, not inside JS string literals — use real characters in strings.
- **Phone testing on LAN** requires the computer's IP in `allowedDevOrigins` in `next.config.ts`. If the IP changes, the dev server's `Network:` startup line shows the new one.
- **Stray `.ts` files in the project root** get type-checked by `next build` and fail because of `allowImportingTsExtensions`. Don't leave temp scripts there.
- **CSS transitions don't fire on Tailwind v4 scale/blur utilities.** v4 compiles `scale-*` to `--tw-scale-x/y` variable updates rather than `transform` property changes. For animated zoom/blur, set `transform` and `filter` as INLINE STRINGS in the style prop so the browser sees a real property change.
- **Next.js `<Image>` optimiser can leave a checker pattern on transparent PNGs.** The opt'd-WebP returned the right alpha but the browser still rendered a checker in our test. Workaround: plain `<img>` (with a `?v=N` query string for cache-bust) for transparent assets.
- **Per-property transitions require inline CSS.** Tailwind's `transition-all` shares one duration + delay across properties. To delay the blur after the zoom starts, write the `transition: transform 2500ms … 1000ms, filter 1800ms … 1700ms` string into `style.transition`.
- **CSS transitions need the rules in place BEFORE the value changes.** Setting both the transition AND the target value in the same render cycle makes the browser snap to the final value with no animation. Keep transition style unconditional.
- **Animations synced via `phase_ends_at` must use the absolute timestamp.** Anchoring black overlays / climax effects to `endsAtMs - 500ms` (vs. a local setTimeout from when entering=true was observed) is the only way slow clients don't miss the climax before the phase advances.
